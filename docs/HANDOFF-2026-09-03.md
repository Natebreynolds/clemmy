### B. The exact-checkpoint re-entry storm

**What happens.** A stuck run gets re-entered several times per second, logging
alternating pairs forever:

```
accepted model batch pre-admission failed before tool execution
  (reason: model batch admission requires the exact prior balanced checkpoint)
host retained exact checkpoint recovery ownership
  (reason: host_model_batch_admission_unavailable)
```

454 lines tonight before the daemon was killed. **This predates all of tonight's work:**
pid 45854 = 1,054 lines (09-01 10:50Z), pid 70807 = 1,006 lines (09-01 18:30Z — the
"1,006 re-entries" already in memory), pid 34981 = 40 lines (09-02 17:17Z).

**Correction to an earlier theory.** The budget is *not* "keyed too finely."
`EXACT_CHECKPOINT_REENTRY_BUDGET = 5` keys on
`sessionId:sourceUserSeq:phase:frameCallIds` (`restart-recovery.ts:88-114`) and every
input is provably stable across retries. The key is fine.

**The real reason it never binds:** it gates **one caller's** decision, not the failure
site. It is consulted only inside `recoverInterruptedChatRuns` (`:1276-1280`,
incremented `:1554-1559`). At least two other paths reach the identical failure without
touching the Map:
- `loop.ts:10743-10768` — `runTurn` itself performs one immediate re-entry on **every**
  dispatch, silently doubling attempts;
- `host-turn-runner.ts:5555-5563` — the legacy approval-resume admission path.

And the eligibility query (`eventlog.ts:1164-1187`) has **no attempt counter, no
cooldown, no last-tried column**. A failed retry rewrites the same stuck
`__host_recovery_state` blob, so the row matches again on the next 15s tick
(`daemon/runner.ts:3371-3374`), forever.

**Underlying permanent state (inferred, well-evidenced):** the frozen recovery blob's
`history` / `lastResponseId` no longer match what `accepted_model_batch_checkpoints`
holds. The retry path never re-derives them from the live table — it only replays the
frozen copy — so the SQLite trigger `trg_accepted_model_batch_admission_chain`
(`eventlog-schema.ts:2884-2943`) rejects every attempt identically. It cannot self-heal.

**FIXED 2026-09-03.** The diagnosis above is correct and the fix follows it, with one
widening found while implementing:

- The budget moved out of `restart-recovery.ts` into a dependency-free leaf module,
  **`exact-checkpoint-reentry.ts`**, so the host runner and the scanner share one Map
  without the import cycle (restart-recovery → delivery-committer → host-turn-runner).
  `restart-recovery.ts` re-exports it, so every existing import still resolves.
- The counter now spends **where a retry fails**, not where a caller dispatches. The
  scanner's increment is gone; `recoveryOutcome` (`host-turn-runner.ts`) owns it, and the
  legacy approval-resume path — which bypasses `recoveryOutcome` — spends it directly.
  All three entry points converge on one count.
- On exhaustion the hold becomes `blockedOutcome(…, 'exact_checkpoint_admission_exhausted')`.
  A blocked outcome carries **no** `serializedRecoveryState`, and `loop.ts` re-enters only
  `outcome.hold && outcome.serializedRecoveryState` — so the immediate re-entry and the
  15 s tick both stop there.
- **The widening.** Counting only the admission failure would have *narrowed* the guard:
  the scanner's old dispatch counter also bounded `host_result_checkpoint_mismatch`,
  reopen-unavailable, and `recovery_surface_unavailable:*`. Budgeting at
  `recoveryOutcome` covers all of them, and `boundedRetry` defaults to **true** so a new
  failure reason added later cannot silently reintroduce an unbounded loop. Exactly one
  caller opts out — `durable_async_read_continuation_pending`, a paging read that
  re-enters the same key **by design** while advancing on its own durable cursor. Without
  that opt-out a 6-page async read would have terminated at page 5.
- Pinned by `host-turn-runner.test.ts` — "a permanently unadmittable frame spends one
  shared budget and stops with a typed terminal". It reproduces the live failure with a
  TEMP TRIGGER that aborts inserts into `accepted_model_batch_admissions`, and asserts the
  key the **runner** spent is the key the **scanner** derives from the serialized blob. That
  last assertion is the one that matters: if the two derivations ever drift the budget
  silently stops binding and the storm returns. Verified red before the fix (fails on
  attempt 5 by holding forever), green after.

**Headroom note.** The budget is 5 *failed attempts*, and `loop.ts` performs one
immediate in-process re-entry per dispatch, so a permanently stuck frame now stops after
roughly 2–3 dispatch cycles rather than 5. That is deliberate — `admitAcceptedModelBatch`
already retries itself once internally for a transient SQLite failure, the terminal is
`resumable` (the user's next message or a restart retries it), and nothing is discarded.

**Residual, deliberately not fixed.** The poisoned `__host_recovery_state` blob is *not*
cleared on exhaustion, so a daemon restart resets the in-process Map and the session will
storm 5 more times before stopping again. Clearing it blindly is unsafe: `recoveryOutcome`
also covers reasons where an external effect may have landed. Converging that needs a
durable attempt counter (or a cooldown column) on the eligibility query at
`eventlog.ts:1164-1187`, which has none. Before restarting the daemon on the stuck session,
clear its `__host_recovery_state` by hand.
