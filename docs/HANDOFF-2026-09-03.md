## 1. Do these two first — they are why the last run died

Neither is a gate. One is a missing deadline; one is a counter in the wrong place.
Both are small and independent of everything else in this document.

### A. A turn can go silent forever after a tool frame settles

**What happens.** `host-turn-runner.ts:6036` calls `await refreshTools()` unconditionally
at the top of every step, with **no deadline**. It reaches the SDK's
`Agent.getAllTools()` → `getMcpTools()`, which does a live `tools/list` round trip to
every attached MCP server.

Nothing watches it. The stall watchdog is built inside `runOneModelStep` and torn down
the instant the model call settles (`:2906-2907`) — it covers the model and nothing else
on that path. `withActiveTurnHeartbeat` (`loop.ts:9189-9220`) fires on its own timer and
reads nothing about progress, so a wedged turn emits "still working" every 3 minutes
forever. That is exactly what run 5 did: 13 minutes of heartbeats, zero log lines.

**Fix.** Wrap that one await in the deadline pattern already used 60 lines below it —
`recoverCommittedMutationVerificationsForSource(..., deadlineMs: hostToolDeadlineMs('work_call'), callerSignal: signal)`
at `:6097-6105`. On expiry: log, and return a typed resumable outcome.

**Loose end worth 10 minutes.** Clementine's own MCP shim IS bounded
(`mcp-namespace-shim.ts:1141-1145`, 20s), so worst case there is ~30s, not 13 minutes.
Nobody confirmed whether the production orchestrator `Agent` attaches `mcpServers`
directly (unbounded SDK path) or pre-flattens tools at construction. Check
`buildOrchestratorAgent` (`src/agents/orchestrator.ts:1791`). **Note: eight remote MCP
servers failed to connect during this session** (n8n, pinecone, apify, brightdata,
dataforseo, mcp-server-chart, shadcn, vapi). A `tools/list` to a dead server on the
unbounded path is precisely this hang.

### B. The exact-checkpoint re-entry storm

**What happens.** A stuck run gets re-entered several times per second, logging
alternating pairs forever:

```
accepted model batch pre-admission failed before tool execution
  (reason: model batch admission requires the exact prior balanced checkpoint)
host retained exact checkpoint recovery ownership
  (reason: host_model_batch_admission_unavailable)
```

454 lines tonight before the daemon was killed. **This predates all of tonight's work:**
pid 45854 = 1,054 lines (09-01 10:50Z), pid 70807 = 1,006 lines (09-01 18:30Z — the
"1,006 re-entries" already in memory), pid 34981 = 40 lines (09-02 17:17Z).

**Correction to an earlier theory.** The budget is *not* "keyed too finely."
`EXACT_CHECKPOINT_REENTRY_BUDGET = 5` keys on
`sessionId:sourceUserSeq:phase:frameCallIds` (`restart-recovery.ts:88-114`) and every
input is provably stable across retries. The key is fine.

**The real reason it never binds:** it gates **one caller's** decision, not the failure
site. It is consulted only inside `recoverInterruptedChatRuns` (`:1276-1280`,
incremented `:1554-1559`). At least two other paths reach the identical failure without
touching the Map:
- `loop.ts:10743-10768` — `runTurn` itself performs one immediate re-entry on **every**
  dispatch, silently doubling attempts;
- `host-turn-runner.ts:5555-5563` — the legacy approval-resume admission path.

And the eligibility query (`eventlog.ts:1164-1187`) has **no attempt counter, no
cooldown, no last-tried column**. A failed retry rewrites the same stuck
`__host_recovery_state` blob, so the row matches again on the next 15s tick
(`daemon/runner.ts:3371-3374`), forever.

**Underlying permanent state (inferred, well-evidenced):** the frozen recovery blob's
`history` / `lastResponseId` no longer match what `accepted_model_batch_checkpoints`
holds. The retry path never re-derives them from the live table — it only replays the
frozen copy — so the SQLite trigger `trg_accepted_model_batch_admission_chain`
(`eventlog-schema.ts:2884-2943`) rejects every attempt identically. It cannot self-heal.

**Fix.** Move the counter to the choke point: `preAdmitAcceptedToolFrame`'s failure
branch, `host-turn-runner.ts:4784-4797`, keyed the same way. When exhausted, return a
**distinct typed terminal** instead of a hold that invites the next caller to retry.
That converges every entry point on one durable stop.

  `args_json`/`args`/`arguments`/`input`/`params`, direct calls by slug), resolved

  `frame_refused` with the raw carrier shape; `blockedOutcome` logs every reason; a

- **BYO siblings rescue a BYO primary** (`byoSiblingTargets`, cap 2) — grok can now fall

### Measured, from run 5 (`model_route_metrics.db`, real bytes)

`stablePolicy`, `turnContext` and `memoryContext` were **byte-identical across all four
requests** — the prefix caches well. All growth is `task`.

### What the field says (2026)

- **Tool search is correct — do not preload.** Anthropic's own MCP-eval: 49% → 74%
  (Opus 4), 79.5% → 88.1% (Opus 4.5) *with* a tool-search tool. It also lowers TTFT by
  keeping the initial context light and maximizing cache hits.
- **The complement is semantic pre-selection**: ~99.6% reduction in tool tokens at 97.1%
  hit rate for top-3, sub-100ms. Hermes has this as an **open** issue (#13332, "Hybrid
  Tool Pre-Selection… without extra LLM round trips") — a place to be ahead.
- **Memory: hybrid.** "Retrieving some data up front for speed, and pursuing further
  autonomous exploration at its discretion." Injecting is right; *inviting a re-fetch* is not.
- **Long horizon:** just-in-time identifiers + compaction + note-taking. Result handles
  and `tool_output_query` are exactly that; Clem has it.

### Verified facts about our own layers

- **Composio operations are genuinely excluded from turn 1.** `tool-registry.ts` has only
  4 generic gateway tools (`composio_execute_tool`, `composio_list_tools`,
  `composio_search_tools`, `composio_status`). Turn-1 catalog membership is decided by
  `resolveHotSet()` (`tool-catalog.ts:165-203`): 6 always-loaded + literal name matches +
  named workflows + ≤3 memory-pinned + ≤3 session LRU.
- **A capability advisory card already exists** — `resolveTurnCapabilityCandidates()`
  (`read-path/capability-candidates.ts:773`), lexical + optional semantic, rendered as
  names/roles into **turnContext** via `renderCapabilityCandidateCard()` (`:1096`).
  **But it is gated on prior successful use.** A first-time-connected operation surfaces
  nothing. `connected-goal-catalog.ts` likewise enumerates schemas already in the contract
  store from *earlier* searches — not eagerly at OAuth-connect time.
- **Cache invalidation order** (`prompt-cache-observation.ts:247-289`):
  `transport → stablePolicy → turnContext → memoryContext → catalog → task`; the earliest
  changed layer invalidates everything after it. **Wire caveat:** on the real Anthropic
  wire, tools precede system, so a tools-array change busts the *whole* cached prefix
  (`claude-model.ts:296-299`) — the harness's internal accounting is more optimistic than
  the wire. **Therefore: put an inventory in `turnContext` as names, never schemas in the
  tools array.**
- **`DEFAULT_TOOL_RESULT_MAX_CHARS = 20_000`** (`tool-output-format.ts`) decides how much
  of a result reaches the model before it digests and parks. It is **flat** — tuned for a
  200K window, running on a 2M-window brain. Its neighbours already scale:
  `fanoutDigestThreshold` = `8 × windowScale`, `envelopeDigestMax` = `700 × windowScale`.
  **Making this consistent is a one-line, well-precedented change.**

### The recommendation

**Turn 1** — keep it light; add *identifiers, not schemas*, into `turnContext`:
connected toolkits by name, the skills index (names + one-liners), and the top-K
operations semantically matching the ask. Seed the matcher from the **connected-toolkit
catalog**, not only from proven history, or a newly connected tool stays invisible.
Roughly 1–2KB on a 38KB turn, removing 2–3 round trips. Schemas still arrive via
`tool_search`.

**Later turns** — scale `DEFAULT_TOOL_RESULT_MAX_CHARS` by `windowScaleForModel`, and
keep offloading through handles + `tool_output_query`.

**Also fix:** the `[MEMORY PRIMER]` contradiction. `turn-primer.ts:176-180` labels recall
`partial`/`insufficient` and says "call `memory_recall_all` (one call)", while
`clem-rubric.ts:164` says "use memory without archaeology — the injected blocks are the
runtime's bounded retrieval result." **Note:** the primer is used by the Claude-brain,
legacy-loop and plan-first lanes — **not** the orchestrator lane run 5 used, whose memory
context carries no answerability label. So the contradiction is real but did **not** cause
run 5's opening `memory_recall_all`; that call is still unexplained.

## 5. The 25-email task (the real target)

> "Help me write 25 sales emails. Find me the most relevant prospects in Salesforce, use
> this skill to write prospecting emails, and use this composio tool to pull SEO data."

Harder than platform-49 in three ways: **three tool families at once** (Salesforce CLI,
a skill, a composio SEO tool), **fan-out over 25 units**, **25 external writes at the end**.

- **Salesforce is CLI-only** — owner rule, never composio.
- **Skills are binding** — MCP/CLI give access to a live system; a skill teaches *how to
  do the task*. Research also finds a skill on a **dedicated** agent beats the same skill
  on a generalist — argues for the email skill riding the fan-out worker, not the parent.
- **The fan-out machinery exists and IS wired** — `fanout-reduce.ts`, imported by
  `worker-tools.ts` and `orchestrator.ts`, swept in `background-tasks.ts`, sharded in
  `workflow-runner.ts`, default on. Design: first K verbatim → compact envelopes with
  reader pointers → async shard reducers into durable artifacts. Errors are never
  digested; coverage comes from the ledger, not the reducer.
  **Measure on the first run:** on grok the threshold computes to `8 × 4 = 32`, so all 25
  results would return **verbatim** and the digest tier would never engage. That may be
  fine on a 2M window; decide from the measurement.
- **Expect trouble at the tail.** 25 drafts = 25 external writes. Memory records a
  draft-batch ambiguity root cause as "solved-not-fixed". Confirm batching into **one**
  approval before running, not during.
- **First-run gap that bites this task specifically:** the advisory card and matchers are
  gated on prior successful use, so the *first* time you connect DataForSEO and
  immediately ask for work is the slowest possible path. That is exactly this task.
