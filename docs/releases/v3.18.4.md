# v3.18.4 — a workflow that cannot run says so, and the console stops waiting on itself

Release type: correctness and performance fixes on top of v3.18.3. Three threads
from three sessions on one branch.

## A workflow that could never run, and said it completed

A scheduled inbox triage failed twelve consecutive runs without once executing a
step, while its own records reported success. One misconception produced the
whole failure, repeated at three layers: **a provider operation is not a tool,
and every layer was looking for a tool.**

The workflow was authored with `allowedTools: [OUTLOOK_LIST_MESSAGES]` — the
honest, obvious thing to write.

**The authoring gate saw nothing to test.** It decided whether a step reaches
real data by matching carrier prefixes (`composio*`, `mcp*`, `firecrawl*`…).
An operation name matches none, so the step was judged local-only, the workflow
needed no creation test, and it was enabled directly — the gate that exists to
prevent exactly this was told there was nothing to check. Both enable doors, the
tool path and the console endpoint, asked it the same question and got the same
wrong answer.

**The runtime lock removed the carrier.** A step's `allowedTools` filters its
tools by NAME, and the operation's carrier is `composio_execute_tool`. Naming
the operation therefore stripped the only thing that could execute it, leaving
the step six structural channels and a list it could not call. The blocklist
directly above that code warns about this in its own words — "curating an
allow-list of WORK tools is the anti-pattern" — and the per-step lock had
reintroduced it one level down.

**The terminal status called the result completed.** A run whose every step was
blocked wrote `status: 'completed'` and summarised itself as "completed 3
steps", with `blockedSteps` attached as decoration — a field whose own comment
says it exists to stop a mechanically-finished run masquerading as successful.
19 of 166 run records on disk carried that lie. The ledger and the owner's Slack
and Discord notices were the only honest channels.

All three now understand operation spelling, and a blocked run reports blocked
with its blocked step named.

## Stalls that could not be seen or stopped

**One automatic retry, then it waits for a person.** A single transient provider
check failure — the revalidation call threw; the account was fine — parked a run
which the reaper then re-admitted every fifteen minutes all night, ten times,
while the drain re-dispatched its step every fifteen seconds. The run never
terminated, so that workflow's later scheduled occurrences never fired at all.

**A pause says what actually happened.** Three distinct refusal codes —
connection missing, connection inactive, and "the check itself threw" — all
printed "Open Settings → Connections and reconnect X". Two of them cannot be
fixed in Settings. A transient check failure now names its own retry time, a
missing account choice says the connection is fine and points at the choice, and
a genuinely dead toolkit keeps the reconnect instruction it has earned.

**The board stops disguising a stuck run.** A workflow card's age was keyed to
its last event, so a run stuck for ten hours rendered as 39 seconds old on every
poll. One piece of work also produced two cards — a workflow card and a run card
— with two different cancel behaviours. Age is now real duration, and the
duplicate collapses into the workflow card.

**Finished work moved below the live work.** Done was a fourth column of up to
forty terminal cards sitting between what is running and the shelf that already
answers "what has she made me". Live columns are the grid now; Done keeps its
lane below, collapsed behind a count.

## The console stops waiting on itself

`/api/console/sessions` took **14.6 seconds** to answer. The cost scaled with the
page, not the table — about 110ms per returned row — because the workflow-run
lookup paged through the entire session table once per row it returned, roughly
66,000 redundant reads against 1,469 sessions, when the scan one line earlier
had already paid for exactly that and thrown it away.

Measured on the live home: **14,712ms → 460ms**, and a 100-row page now costs
only 70ms more than a 10-row page. The quadratic is gone. Output was diffed
row-for-row; this removes work rather than changing behaviour.

## Home is the command center

The briefing no longer lives on `/chat`. Live work shows the step she is on
instead of a stack of empty peeks, finished work is a dated folder you can open
from Home, model rows stay inside the picker, and a live turn no longer leaves a
hollow reply.

## Plan mode

The plan you approve is the plan that runs: a plan published for review is
deliberately unbound, so its card now offers "Approve shape & prepare to run" —
exactly when Execute cannot be offered — and the binding lands as a revision of
that same plan.
