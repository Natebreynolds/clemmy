# v3.18.3 — a Plan turn owes you the plan before it does the work

Release type: behavior fix to Plan mode on top of v3.18.2.

## What was wrong

A Plan run opened with a research brief and a linked Google Doc. Clem read the
doc 95 seconds in — correctly — and then spent the next six minutes doing the
research: seven live searches, 23 tool lookups, 22 re-reads of her own results,
about two thirds of the turn on discovery. She hit the per-turn tool ceiling and
never published a plan at all. The owner stopped it and said what he had
expected: read the document I gave you, then tell me what you're going to fan
out to do, and don't start until I say go.

Nothing she did was against the rules. Plan mode's only ceiling was external
consequence — every read was allowed, deliberately, because earlier runs
collapsed when a planning turn was refused a read it needed. What was missing
was the other half: nothing ever required the plan itself, so a planning turn
was free to spend its whole budget executing the work it was supposed to be
proposing. Two instructions made it worse by disagreeing with each other — the
turn objective led with "Investigate", and the plan-mode instruction beside it
asked for a fully bound execution artifact, which is a compiler spec.

## What changed

**The plan comes first.** Both instructions now say the same thing in the same
order: read every input the user named, use what memory and context already
hold, then publish promptly the plan a person can review — what those inputs
said, the steps to fan out, what each produces, which roles run them, order,
dependencies and verification. Bind what is already in hand; name the rest as
`needs_input` prerequisites, or ask the user that exact question instead of
gathering the answer. The full binding pass becomes a revision of that same plan
once the shape is approved.

**Reading your own inputs is never the work.** A target named in the user's own
request — the document id they pasted, the sheet they linked — is an input:
unmetered, always readable, and never a plan step. "First I'll read your
document, then I'll plan" is not a plan, and this boundary is what stops a turn
from having to offer one.

**Doing the work before proposing it is.** After a small scoping allowance,
external reads that the user never named refuse with both doors named: publish
the plan, or ask the question. Host-local calls — memory, context, catalog — are
never metered, and a turn that has published is unconstrained.

**The budget verdict says what the harness does.** The preflight budget event
still read "turn should be refused or routed through plan-mode" long after that
steer was removed for causing more harm than it prevented. It is telemetry: the
turn proceeds and compaction owns context size. The stale wording produced a
wrong diagnosis of this very run within minutes of being read.

## What was already true

Nothing needed building for the rest of the path. A plan can be published as
readable text with a readiness flag — the fully structured form is optional,
`needs_input` is first class, and revisions carry a base. Published plans reach
the user as a review card with an Execute button, and execute mode binds every
effect to a step in the reviewed artifact, so approval is a real gate.

## Known limit

A plan published as shape only has no bound steps, and execution matches each
effect against a bound step. Approving a shape-only plan therefore needs a
binding pass before it can run — either a revision after approval, or binding at
execution time. That decision is open; it does not affect producing or reviewing
a plan.
