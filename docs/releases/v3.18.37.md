# v3.18.37 — a provider that replied is read, never reconciled in the dark

Harness schema stays at 93; no database migration. The Mac build comes from
the release workflow (signed and notarized). The Windows x64 build of the same
commit is qualified by the private Windows pipeline from this tag and attached
to this release, **unsigned** until a code-signing certificate exists: a fresh
Windows install shows SmartScreen's "Run anyway"; updates install normally.

One thing drove this release: the owner's rule that there is never a world
where Clem stops with "The tool stopped after execution may have begun. I
preserved the call as uncertain and blocked replay" and the harness speaks for
itself. The stop he hit on 2026-10-12 (an approved AIBS site creation the app
refused) was traced through the ledger to two readers of the same reply that
did not agree, and both are class rules now.

## A provider that replied is read

- **A refusal that arrives as a throw is still an answer.** A native MCP
  error reaches the host as a thrown error. The settlement already read it as
  the provider's own refusal, but the checkpoint and the runner's thrown-call
  classifier trusted only replies that came back as results: the model was
  handed a blank "effect unknown" marker and the turn ended in host prose,
  with the owner never shown what the app had said. Now the model receives
  the provider's words as the call's result, with what the ledger already
  enforces: nothing is known to have landed, read the target if it matters,
  change what was refused before trying again, this exact call is not
  resent. The turn goes on and Clem answers in her own words.
- **Two readers of one reply never kill the attempt.** A mutating reply can
  be a success by protocol (an MCP result with no error flag) and a failure
  by its own bytes (a body that says `success: false`, an error field, a
  non-HTTP failure code). The classifier read the protocol, the result-handle
  facts read the bytes, and the settlement store turned the disagreement into
  an exception. The attempt died before its settlement existed; the frame's
  receipt could not be recorded; five retries spent the checkpoint budget;
  the turn ended "I could not reopen the saved checkpoint"; and a reaper
  settled the call "unacknowledged" twenty seconds after the owner had been
  told. The same shape as the 2026-09-04 DataForSEO disagreement. Such a
  reply now settles as the provider's own contradiction: an uncertain write
  whose bytes are retained for the model, with no success handle and no
  replay, and the turn goes on. The model reads the reply, reads the target
  before saying anything landed, and answers. Every reader of that
  settlement agrees now: the runner, the checkpoint, the audit and the
  no-progress governor (which, live, was the last to still send the
  contradiction to a reconcile stop).
- **What is still the dark.** A reply that never came (a dropped connection,
  a timeout mid-flight) still stops the turn to reconcile before any retry.
  That stop is next.

## A workflow's write review decides, it never loops

- **Two refusals, then a decision.** A scheduled sheet review appends one
  digest row each run. On 2026-10-13 its write was refused six times in ten
  minutes by the step's own constraint review, each time for a different
  reason (a count, the date style, "the inspected tail does not establish
  absence"), re-read, re-proposed and refused again until the run was
  cancelled by hand; the previous day's run had ended the same way, and the
  owner's sheet got no row either day. The reviewer was judging a compacted
  view of the evidence while demanding completeness, and nothing bounded
  the rounds. Now an "uncertain" verdict on a recoverable write is asked once
  more with the whole retained evidence before it counts (a send still gets
  exactly one review, at full stakes); the reviewer is told to name every
  objection at once; and after two refusals of one step's write, the review
  decides. A recoverable write proceeds, and the checker's last objection
  rides to Clem with the result so her report says it; a high-stakes write
  stops truthfully as not done, with the objection quoted, for the owner to
  decide. The step never loops and never ends in host prose.

## No hoops on the first call

- **A server that is still connecting is waited for, not reported.** The
  first live turn after an install asked for one connected server's delete
  tool. That server starts as a package launch plus a remote handshake, past
  the per-turn attach budget, so the discovery search handed Clem a
  "connecting, available in a turn or two, tell the user it's warming up"
  stub. She paged the stale stub, guessed at two host tools, reconnected the
  server (which dropped every server's connection and restarted the warm-up),
  searched into the same stub again, and found the tool on the fifth search:
  nine discovery calls and ninety seconds before a one-second delete. Now a
  search holds for a warming server until its own deadline and returns the
  real tools; the stub, when a server is genuinely slower than that, names
  the search as the door and says it is not an outage; and a reconnect by
  name drops and restarts that one server, leaving the others connected.
