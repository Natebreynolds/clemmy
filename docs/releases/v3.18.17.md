# v3.18.17 — spelling is not identity

Release type: defect-class removal. Every change was root-caused from one live
workflow run and ships with that failure replayed as its regression pin. Two
proposed fixes were REVERTED during this wave because their red-before proofs
would not go red; one further change was backed out after it broke settlement
tests. Nothing shipped here that could not be shown to change behavior.

## The defect

The framework decided *"is this an operation, and what performs it?"* in 21
places, every one by testing the name against Composio's spelling convention
`/^[A-Z][A-Z0-9]*(?:_[A-Z0-9]+)+$/`. A reviewed CLI read is lower_snake
(`salesforce_sf_soql_query`), so those sites answered "not an operation" for it.

One workflow — `friday-sales-leadership-email`, first step a Salesforce CLI
read, last step an email — hit twelve of them in sequence. Each produced a
different symptom, which is why it read as twelve bugs rather than one:

*no tools advertised* → *discovered but not executable* → *no salesforce
connection* → *not materialized* → *discovered but not executable*.

The reason it kept returning is that each previous repair ADDED a spelling
instead of removing the test. The 2026-09-11 fix added an UPPER_SNAKE branch;
the 2026-08-27 fix added a carrier-keeps rule. Both were still present, and both
were re-broken on 2026-09-18 by the next carrier.

## What changed

**One owner for identity.** `operationIdentity(name)` answers from what an
operation DECLARES — the current callable catalog, the reviewed-read descriptor
registry, then the shipped CLI catalog — returning `{ operationId, providerKind,
effect }`. It has no shape fallback: a name no registry carries is not an
operation. Proven for all four provider kinds (`local_registry`, `composio`,
`native_mcp`, `reviewed_cli`).

**Four sites converted**, each with a red-before proof:

- **Reachability** (`callable-surface`) decided dispatchability from two name
  shapes, so every reviewed CLI read reported `reachable: false` with a null
  carrier while its manifest sat in the catalog declaring both. Carrier now
  comes from one table keyed on the declared `providerKind`.
- **Discovery budget** (`discovery-boundary`) recognised an operation named in
  prose only when it was MCP-namespaced, so a query naming a CLI read outright
  was charged as broad exploration — spending the task's one allowance on a
  lookup that explored nothing.
- **Validation** (`workflow-validator`) warned about an unverifiable tool only
  when the name was composio-shaped, so a step calling a lower_snake operation
  with a wrong id got no warning and found out at dispatch.
- **Creation-test gate + step tool surface** (`workflow-enforce`,
  `workflow-step-agent`) each carried their own copy of "ask the registries,
  then fall back to spelling"; both now call the one owner.

**Six live-found execution fixes** (`22b810a7`), each observed in a real run:
a workflow step passed `undefined` for `planningIdentity`, so the reviewed-CLI
live-read discovery source was null for every workflow step that has ever run;
a lock naming a non-MCP operation collapsed the MCP scope to null and silenced
all discovery including non-MCP sources; the live-read source hardcoded
`work_call` while ignoring its own carrier parameter, and a workflow step has no
`work_call`; the composio exact path uppercased any snake_case token and claimed
it, refusing a local `sf` read for having "no salesforce connection";
`localPlanningRowStatus` answered "unmaterialized" before consulting the
carrier; and a locked step mounted no `call_tool` dispatcher.

**A guardrail that keeps it.** `npm run check:operation-identity` fails any file
testing a name against composio's spelling convention unless it is on an
allowlist whose every entry names why its answer is confined to a composio path.
It caught a live site during the wave that would otherwise have shipped.

## Measured effect

On the same live workflow step, before and after:

| | before | after |
|---|---|---|
| tools advertised to the model | 0 | real surface |
| `tool_search` calls | 12 | 1 |
| discovery classification | `broad_discovery` | `exact_schema_refresh` |
| Salesforce queries executed | none | real SOQL, `exitCode: 0` |

## Honestly deferred

- **`friday-sales-leadership-email` does not yet complete end to end.** It now
  executes real Salesforce reads; it then stops at the exact-checkpoint re-entry
  budget (`recovery_pending`, `resumable: true`). That budget is an infinite-loop
  guard with a daemon-killing incident behind it and resets on genuine progress,
  so it is not raised here. Whether a looping drain resumes the step to
  completion is UNMEASURED — the probe used during this wave drains once, while
  the daemon loops.
- **Discovery is not yet ranked by procedural memory.** `tool-choice-store`
  records what Clem used successfully; `tool_search` still does not read it.
  Wiring it was implemented and backed out when its import proved to have
  side effects that broke three settlement tests.
- **The 108-file carrier-literal census is untouched.** Separate wave.
- Five of the original 21 sites were reclassified as legitimately
  composio-scoped, one as unreachable; two proposed changes were reverted. The
  real defect was smaller than the census suggested, and the plan in
  `docs/SPELLING-IS-NOT-IDENTITY-PLAN-2026-09-18.md` records each correction.

Unrelated to this release: Outlook's Composio connections are `EXPIRED`, which
is why `daily-standup-email` and `scorpion-inbox-triage` have blocked since
09-16. That is a credential to reconnect, not a code defect.
