# v3.18.57 — Working records decay off the loop; every reference into the event log indexed

**Database migration: harness schema 100 → 102.** v101 adds one small table
that records a retired turn and rewrites nineteen delete guards to read it;
v102 adds forty partial indexes over the columns that reference an event row.
Neither touches a row; both run at the first start of this build (the index
build takes a few seconds on a large install). A build older than this one
does not open a schema-102 database, so a Mac that has started v3.18.57 stays
on v3.18.57 or newer. The Mac build comes from the release workflow (signed
and notarized). The Windows x64 build of the same commit is qualified by the
private Windows pipeline from this tag, unsigned until a code-signing
certificate exists.

Proven on the installed app: every step below was hotpatched onto the owner's
running Mac and measured against its live database and daemon loop.

## What a retired conversation keeps

Memory — facts, preferences, episodes — is never a candidate for deletion.
v3.18.56 let a chat retired to its memory shed the batch records its turns
wrote. This release finishes the job.

- **A retired chat sheds everything it wrote while working.** A day after a
  chat retires (idle a month, its summary written by your memory model), its
  call settlements and evidence, result handles, request provenance and
  retained tool outputs go with the step records. The transcript you read,
  the calls and dispatches themselves, and the memory stay.
- **A watch, a workflow or a workspace sheds a finished turn.** These
  sessions run turn after turn and never retire as a whole, so a turn whose
  work closed thirty days ago, with no run still open, sheds the same
  records. On the owner's install a third of the result-handle bytes were
  theirs.
- **The retirement is recorded before anything goes.** One table names each
  retired turn; every append-only guard on those records reads it and
  nothing else, so a live turn's records cannot be deleted by any path.
- **Diagnostic rows age out of the event log.** Transport timing, prompt
  composition, guardrail notes, discovery decisions and the like are read
  within their own turn; rows older than a month go, two thousand a minute
  until caught up. Dispatch start and settle events and the attempt a call
  settled on are part of the call record and stay with it.

## Nothing waits behind a delete

- **Storage decay runs in a worker.** The decay pass and the diagnostic reaper
  run every minute in a short-lived worker with its own database connection,
  two seconds of bounded work a pass, resuming where the last pass stopped.
  The daemon's loop, which every chat send waits on, no longer holds for it.
  Measured: the first unbounded pass held the loop for 51 seconds; the shipped
  shape holds it for nothing.
- **Every reference into the event log is indexed.** Forty columns across
  thirty tables name an event row and none had an index; deleting one event
  read each of those tables row by row, which once pinned the daemon for
  eleven minutes. Each is now indexed where it is set.

Measured on the owner's install over one evening: result handles 630 → 404
MB, request provenance 254 → 164 MB, retained tool outputs 763 → 494 MB
(logical sizes; the file shrinks at the next offline rewrite).

## Not in this release

- Call and dispatch records of retired turns (small) still stay; their
  start, settle and attempt events stay with them.
- The conversation compaction pass still runs on the daemon loop (about two
  seconds, five minutes after start); it moves to the same worker next.
