# v3.18.50 — an approval card says what Clem will do, a workflow that feeds a Space stops failing, and Clem's reviews and Jev show where you can see them

**No database migration** (harness schema stays at 99). The Mac build comes
from the release workflow (signed and notarized). The Windows x64 build of
the same commit is qualified by the private Windows pipeline from this tag,
**unsigned** until a code-signing certificate exists.

## The approval card says what Clem will do

- **One plain sentence leads the card.** Under "What I'll do": the action,
  the record it touches by name, the app, and who will see it. For example,
  "Add a public note to Frank Tarantino's Greenhouse record with the debrief
  below." The exact content stays under it. Desktop and phone, on every
  card, including the card for a command that leaves this computer. On a
  card that groups several actions, each one is titled by what Clem will do
  instead of its tool name.
- **Names come from the conversation.** The card's writer reads what Clem
  last told you, so a record she named ("Frank Tarantino — candidate id …")
  is named on the card. A card for Frank's record no longer reads "Darrin's
  candidate record"; with nothing tying a name to an id, it says "this
  candidate" instead of guessing.
- **The content is checked whole.** The standing-rules check reads each
  field in full, not the card's 2,000-character preview, so a long note is
  never flagged as "cut off mid-thought".
- **The words being sent show open.** A note or email body shows as a page
  on the card instead of behind "Show the full body". Scripts and raw data
  still fold.
- **Ids stored as numbers are named.** A record that carries an id as a
  number now matches the card's id.

## Clem answers what you send as a run ends

- **A message that lands as a run finishes goes out on its own.** It used to
  join the run as an addition, go unread, and sit under "your message is
  kept" with nothing to send it on. It now goes out as its own message when
  the run ends, once, whichever window sends it; after a question, a card, a
  plan or a Stop it waits with Send now.
- **A question is shown once.** A reply that opened and closed on the same
  question shows it once, after Clem's words.

## Recordings and failed runs read true

- **A recording cut off by a restart still gets its transcript.** A capture
  finalized after losing its ended event now has its Recall upload checked,
  the way a normal recording-ended does. Before, it could sit at "upload
  pending" for good while Recall held the finished recording.
- **A run a restart interrupted no longer blames the keychain.** When the
  service restarts mid-step and Clem rightly does not re-run a step that may
  have written, the message says that, without a locked-keychain line in
  front of it.
- **A notification whose save failed is no longer reported as sent.**
  Since 10-20 the notification store kept its parsed list between reads,
  and a save that failed on disk still showed the new notification, so a
  report-back believed it was delivered and never retried. A failed save
  now drops the kept list and the next read is from disk.
- **A project's conversations list in one order everywhere.** Two
  conversations updated in the same instant could swap places between the
  project page and the projects list; both now break the tie the same way.
- **An approved action runs the call that was checked.** A call Clem sent
  with its details under the shorter of two accepted names was read with an
  extra copy of those details, so its approval no longer matched the call
  that was inspected.
- **read_file's description stays lean** (the relative-path sentence is
  shorter).

## Workflows stop wasting runs

- **A workflow can refresh the Space it feeds.** A Space refresh inside a
  workflow step was refused on every run, so a channel review that ends by
  refreshing its board scored 67% and re-ran the whole workflow. It now
  refreshes; a read-only step still cannot write.
- **No re-run that cannot succeed.** When a goal falls short because the
  workflow's own permissions refused a call, the run reports the gap
  instead of running the whole workflow again into the same refusal.
- **A write reviewed again goes straight to the deciding review.** When a
  write's check answered unreadably and the same write is proposed again,
  the full review decides it without repeating the quick first read.
- **Every write check shows in the run window**, with whether it passed,
  why, and how long it took, on desktop and phone.
- **Clem offers to improve a workflow that keeps falling short.** She sees
  calls a workflow's permissions refused, goal reviews that found a gap,
  and step problems that recur across runs, and can offer the fix on Home
  in her own words.

## Reviews and Jev you can see

- **An answer Jev could not settle is reviewed.** An answer already in
  front of you, which Jev could not confirm, now gets the model review
  instead of shipping "Not checked". It costs you no wait.
- **Jev reads long requests whole** (up to 12,000 characters, up from
  3,000), so saved workflow-step instructions get Jev's quick check
  instead of skipping to the slower review.
- **A memory save the host has already proven** publishes before its
  review.
- **Usage shows the work, the review and Jev apart.** Advanced › Usage
  lists tokens, calls and time by role, and a reply's details show each
  role's tokens and time; Jev's calls read "Jev checks".

## Desktop Memory and the phone

- **Memory** keeps its place while it refreshes, opens a memory in an
  inspector with its evidence and corrections, has an Ask Clem pane, and
  brings the memory graph back as the main workspace.
- **The phone** keeps Send and Stop visible however long the draft, follows
  the keyboard without jumping, uses side navigation on wider windows, and
  loads secondary screens on demand.

## Release health

Nine of the ten tests that had been failing on main since 10-20 now pass.
Five were catching the notification bug above, one the listing order, and
one the approval mismatch above. One timing-dependent pin now stores its
result in production order. Two stale pins now expect the current behavior
(an unchanged task file is not parsed again; the same refusal three times
ends a step). One test still fails only on CI ("durable memory completion
obligation holds pending intake"); it passes locally and has failed on CI
since v3.18.44.
