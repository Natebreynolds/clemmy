# v3.18.50 — an approval card says what Clem will do, a message sent as a run ends is answered, and a recording cut off by a restart still gets its transcript

**No database migration** (harness schema stays at 99). The Mac build comes
from the release workflow (signed and notarized). The Windows x64 build of
the same commit is qualified by the private Windows pipeline from this tag,
**unsigned** until a code-signing certificate exists.

## The approval card says what Clem will do

- **One plain sentence leads the card.** Under "What I'll do": the action,
  the record it touches by name, the app, and who will see it. For example,
  "Add a public note to Frank Tarantino's Greenhouse record with the debrief
  below." The exact content stays under it. Desktop and phone.
- **Names come from the conversation.** The card's writer reads what Clem
  last told you, so a record she named ("Frank Tarantino — candidate id …")
  is named on the card. A card for Frank's record no longer reads "Darrin's
  candidate record"; with nothing tying a name to an id, it says "this
  candidate" instead of guessing.
- **The content is checked whole.** The standing-rules check reads each
  field in full, not the card's 2,000-character preview, so a long note is
  never flagged as "cut off mid-thought".
- **The words being sent show open.** A note or email body shows as a page
  on the card instead of behind "Show the full body". Scripts and raw data
  still fold.
- **Ids stored as numbers are named.** A record that carries an id as a
  number now matches the card's id.

## Clem answers what you send as a run ends

- **A message that lands as a run finishes goes out on its own.** It used to
  join the run as an addition, go unread, and sit under "your message is
  kept" with nothing to send it on. It now goes out as its own message when
  the run ends, once, whichever window sends it; after a question, a card, a
  plan or a Stop it waits with Send now.
- **A question is shown once.** A reply that opened and closed on the same
  question shows it once, after Clem's words.

## Recordings and failed runs read true

- **A recording cut off by a restart still gets its transcript.** A capture
  finalized after losing its ended event now has its Recall upload checked,
  the way a normal recording-ended does. Before, it could sit at "upload
  pending" for good while Recall held the finished recording.
- **A run a restart interrupted no longer blames the keychain.** When the
  service restarts mid-step and Clem rightly does not re-run a step that may
  have written, the message says that, without a locked-keychain line in
  front of it.
- **A notification whose save failed is no longer reported as sent.**
  Since 10-20 the notification store kept its parsed list between reads,
  and a save that failed on disk still showed the new notification, so a
  report-back believed it was delivered and never retried. A failed save
  now drops the kept list and the next read is from disk.
- **A project's conversations list in one order everywhere.** Two
  conversations updated in the same instant could swap places between the
  project page and the projects list; both now break the tie the same way.
- **read_file's description stays lean** (the relative-path sentence is
  shorter).

## Release health

Six of the tests that had been failing on main since 10-20 now pass: five
were catching the notification bug above, and one was the listing order.
Two stale pins now expect the current behavior (an unchanged task file is
not parsed again; the same refusal three times ends a step).
