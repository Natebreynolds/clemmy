# v3.18.23 — projects and the agents that work in them, reviews held to their evidence, and work that is learned

Mac-only release. The full unit suite ran to completion on the code candidate
before these notes were written, and the installed app served that same commit
for the last round of live checks. The remaining release checks were still
running on the candidate when the tag was made, at the owner's word; they are
listed below as running, with their last results on earlier tips. Signed and notarized artifacts
are produced by the release workflow and are not claimed here.

## What changed

### Projects, agents and scoped learning

- Work can be organised into projects. A project has a purpose, goals,
  standing context, the agents assigned to it, the accounts and local projects
  it uses, its conversations and its work. It is made and changed on the
  desktop, on the phone, or by asking Clem. Nothing that already used the word
  "project" changed its meaning: the code folders under Connect are now called
  local projects where a project links to them.
- One saved agent can be assigned to several projects. Each assignment says
  what the agent answers for in that project and holds context that applies
  only there.
- A conversation can work in a project and with an agent, and either can be
  changed mid-conversation. The change applies from the next message; earlier
  replies keep who wrote them and where.
- Work can be delegated to an agent as a task with an owner, a project and a
  request that is versioned. The conversation that delegated it sees each real
  change. A task can be steered, stopped, resumed and answered from either app.
- A correction goes to the owner of the work. An open task takes it as the
  next version of its request. Finished work is followed by a new task for the
  same agent. Work that stopped before it finished resumes in place, and only
  the owner restarts it.
- What is learned is kept for what it was learned in: everywhere, a project,
  an agent, or an agent in a project. A turn sees what is kept for everywhere,
  its project and its agent. The same sentence learned in two projects is two
  records. The owner sees what each memory is kept for and can move it.
- A project links to the local projects its work happens in, from the
  machine's own list. Coding runs started from a project's conversations are
  listed with its work. Linking grants no access.
- The cost of a whole request can be totalled: the request, its helpers, the
  tasks it delegated, the router and the reviewers.
- An agent identity or a project grants no new authority. Approvals, consent
  and standing rules apply to delegated work exactly as they do to Clem.

### Workflows

- A scheduled workflow no longer pauses to ask which account to use when one
  account was only registered more than once.

### Reviews, learning and meetings

- Meeting analysis is saved through a typed host tool into a writable Meetings
  home, and saved transcripts can be searched and read from chat. Attachments
  and tool images survive admission and reach the model that can see them.
- Compatible prepared writes are reviewed as one approval showing each exact
  action, on desktop and phone. A setup call whose effect is uncertain is
  clarified before approval is asked. Approval notices are reused, review
  lineage survives the approval, and a provider reply that contradicts its own
  "no change" acknowledgement is rejected.
- A completion review is held to what it inspected. Its evidence lookups are
  recorded on the verdict. When an acceptance needs the whole of a result that
  nobody read in full, the review is asked once more and then the claim is sent
  back for correction. A bounded list view states how many records it holds.
  A verdict that arrives without its verdict line is restated at low effort
  instead of being reviewed again.
- Work finished after an approval is learned under the request that asked for
  it. Before this, approved work taught nothing. A learned run records the part
  each operation played (prepare, change, verify), so a later run is asked for
  the same check. A run that used only what it was handed adds its proof to
  that strategy instead of becoming a second one.
- When the router leans to the same operation in both of its turn-start
  answers without being sure of either, the remembered run is offered on the
  first frame. Discovery stays available and the tool surface is not narrowed.
- A request's own earlier history no longer crowds standing facts out of the
  memory block at the start of a turn.
- What finished work resolved (the exact value a name stood for) is kept when a
  typed naming check is sure. See the limits below: this did not occur live.
- No provider operation name decides an approval label or lowers consent. A
  returned value is named by what it was made from, read from the settled calls.
  The meeting and image readers stay on the chat planning surface without being
  admitted to durable projects.

## Live evidence

Installed-app checks used the real home and named controlled fixtures. No
personal data was reset or migrated. Pending approvals that were not part of a
fixture were not touched.

- Review evidence: with one read allowed, an answer claimed something about
  all 140 fixture records after seeing about a tenth of the file. The reviewer
  named that read as needed in full and made three lookups before accepting.
  All three are on the verdict record. The reviewer wrote the required line
  both times it was asked.
- Learning from approved work: five controlled sends to the owner's own
  address, each card checked by script before approval. The first approved run
  taught a strategy; none of the four earlier approval-resumed runs in the
  record had. A second, differently worded request received that operation on
  its first frame.
- First-frame effect, one pair: request to approval card 60.1 s then 7.8 s;
  brain prompt tokens before the card 102,469 then 12,911; discovery calls 4
  then 0. The two runs did not do identical work (the first read its send back,
  the second did not), and the second ran warm.
- Verification travels: a run that was not asked to check its send, handed a
  strategy that records a check, read the send back.
- Meeting search was called first from chat for a phrase that matches nothing,
  returned zero, and the run made no change.

Projects, agents and scoped learning, on one synthetic fixture (48 sales
records, 20 applicants), one agent and three projects, across four installs:

- Asked in one message, Clem created a project, assigned the agent and attached
  the conversation. Work asked for in the background inside the project was
  given to the assigned agent by the router as the task started, and finished
  with correct figures. The same task was read on the desktop and on the phone.
- A correction in the same conversation was handed to the owner of the work:
  one task that follows the finished one, for the same agent, done. The
  finished task was not reopened and one draft was written. Reply after 59 s,
  ended done. Before this work the same correction was redone by Clem in the
  foreground and ended blocked after 4 min 53 s.
- A running task was steered, stopped and then corrected: the same task
  resumed at the next version of its request and finished. One task, one file,
  figures recomputed from the source and matching.
- "Who are the leads here?" to the same agent in two projects: opportunities
  in one, two named applicants in the other, each as its own project defines a
  lead. What was learned was kept for the project it was learned in; nothing
  about either fixture was kept for everywhere.
- A follow-up in a new conversation in the project found the draft without
  searching conversation history, in both runs.
- An agent that is not saved starts nothing and Clem says so. Work on a file
  that does not exist starts no task. A background task whose one command was
  refused ended blocked, never done, and is shown as paused with Resume and
  Correct.
- Switching agent and project mid-conversation applies from the next message;
  the reopened conversation keeps each reply's author and project.
- A local project was linked to a project by name; a folder that is not one of
  the machine's local projects, and a partial name, were refused with the list
  to choose from. The link shows on the desktop and the phone, and Clem, asked
  in a new conversation in the project, named the local project and its folder.
- The owner's own pending approvals were counted before and after each
  install and each round: unchanged.

Reviews were served by a substitute for the pinned reviewer model wherever the

substitutes, not as validation of the pinned model. In the project rounds 5
of the first 12 completion reviews timed out and failed open; those results
stand unreviewed and are not counted as validated.

## Known limits

- The workflow account fix was not confirmed live. The state that paused a
  run before (one account registered more than once) was reproduced on the
  installed candidate and a controlled workflow was started, but its result
  was not read. The fix rests on its test.
- An approval raised by a delegated task and declined was not exercised live:
  only an outside write raises an approval card, and none was fired to obtain
  proof. It is covered by route tests.
- A project's list of coding work was not seen populated live.
- Asked to hand work to an agent, Clem may use a helper inside her reply
  instead of a durable task. The agent does the work; no task card exists for
  it. A durable task is certain when the owner names the background.
- Entities, resource pointers, notes and tool contracts are not scoped. One
  known only from another scope's facts is withheld at recall.
- Nothing learned in one project is promoted to another yet. An agent's tool
  list is stored and not enforced. There is no pause: stop and resume.
- A task started by the owner's words names no request, so its cost is
  attributed by its start time.
- The shared chat engine's tests are in no release gate. Run by name with
  the app and project tests, 1,195 of 1,196 passed; the one failure is a top bar
  pin that fails the same way without this work.

- Resolution learning was not observed live. On two builds the naming check
  chose the right name at 0.72 against a bar of 0.80 and nothing was kept. The
  bar was not lowered.
- The offer from two unsure router answers did not occur live. It rests on 7
  historical cases.
- An approval named through the produced-from rule, and the approval that
  returns for opening a conversation by a person's id, were not exercised live.
  Removing the compiled-in declaration means that call asks for approval again
  until the learner is sure of it.
- `meeting_read` and `view_image` were not exercised live after their change of
  declaration.
- One run was slow for a reason that is not recorded anywhere: its remembered
  operations were not published within the provisioning budget. Why is an
  observability gap.
- Verified-write capability learning still reads the approval decision's
  source and learns nothing from approved work.
- The 130-prompt ordinary-conversation benchmark still fails at its third
  sample, as at v3.18.22. Measured on this candidate: 36 samples take the
  no-tool surface, 92 take the full surface (10 tools, 14,689 bytes of tool
  schema, 154 catalog snapshots a turn), and 2 acknowledgements that open a
  conversation are answered with a clarifying question before any model is
  asked. No assertion was weakened. This efficiency target remains unmet.
- 85 older source files still name provider operations. The ratchet only lets
  that count fall.
- Every timing above is one run or one pair. No variability is claimed and no
  universal latency or cost reduction is promised.
- Windows signing remains unconfigured; this tag publishes Mac artifacts only.

Remaining checks stay visible after the tag. No pending check, known failure or
substituted reviewer is relabeled as a successful validation.
