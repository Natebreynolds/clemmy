# v3.8.0 release candidate — closeout evidence

Branch `codex/v3.8.0-release-candidate`. Base for this closeout pass:
`0c088733` (the reviewed SHA). Verdict and frozen SHA are recorded at the end
of this document — nothing above them claims release readiness.

## A. Verified procedural memory

**Learning is a settlement act.** The learn call sits at the end of governed
Composio settlement — after `detectComposioFailure`, after async job-receipt
resolution — and consumes only the FINAL payload (the resolved poll result
when a job auto-resolved; nothing when it parked, failed, or stayed queued).
It must first append a typed `read_receipt` event and then re-resolve it BY ID
through the same resolver production retrieval uses; no durable receipt, no
learning. (`src/tools/composio-read-settlement.ts`,
`src/memory/verified-read-learning.ts`.)

**Typed receipt only.** A 4xx/5xx payload, a thrown dispatch, a
queued-but-unresolved handle, and an unverified body all decline — each pinned
black-box through the real gateway in
`src/runtime/read-path/verified-memory-closeout.test.ts`.

**Identity.** The receipt carries `{tenant: machineId, workspace: home,
accountIdentity}`; the exactly-once claim keys on
`{sessionId, sourceUserSeq, identifier, account}` — a brief that read two
mailboxes is two settlements, and a replay of any one of them loses. Alias
rows key on `(phrase, scope, identifier, account)`, so a multi-read turn keeps
every capability it proved and two accounts keep distinct provenance.
Deliberate design call: `userId` is NOT a retrieval partition — a daemon is
one human across surfaces (desktop↔Discord parity), and partitioning by
per-surface user ids would break exactly the cross-surface reuse this feature
exists for. The install (machine + home) is the privacy boundary.

**Live schema contract.** Learning binds the live per-identifier contract
digest from the same schema cache discovery deposits into, and fails closed
without one. Every retrieval tier (token, exact-alias, semantic) refuses a
stored capability whose live contract has moved until a fresh settlement
re-proves it.

**Turn-bound delivery.** The phrase-keyed global cache is deleted. The bridge
resolves candidates once per accepted turn and binds them ON THE REQUEST;
the Codex lane threads them through the agent build options and the Claude
lane reads the request directly. The predecessor-red proof is an ESTABLISHED
session (prior turns recorded): both brains rank tools against the joined
conversation query there, so the phrase-keyed side channel silently missed —
red at 0c088733, green now
(`src/runtime/read-path/capability-routing-production.test.ts`).

**Candidate card.** Both brains receive a bounded (≤5 line, ~289 byte)
advisory card: kind, exact identifier, intent, provenance (how it matched,
which account proved it) — never prior invocation arguments. Pinned in both
lanes, including the no-argument-leak assertion.

**Aliases one-to-many.** PK `(alias_digest, scope_digest, identifier,
account_identity)`; exact lookup returns every row; the store-level class
CHECK, tamper digest, and scope isolation pins all still hold
(`src/memory/capability-alias-index.test.ts`, 11 tests).

**Durable embedding backfill.** Rows missing a vector ARE the queue (they
persist in SQLite until embedded); settlement arms a debounced drain, boot
warm is the backstop. A paraphrase learned mid-life retrieves on the next
turn with no restart — pinned with a unique-slug isolation so nothing
pre-warmed can fake the pass.

**Measured retrieval cost** (this machine, local `bge-small-en-v1.5`):

| mode | p50 | p95 | hits |
| --- | --- | --- | --- |
| cold (nothing learned) | 0.0 ms | 0.2 ms | — (no candidates, no cost) |
| assisted paraphrase | 3.0 ms | 5.1 ms | 40/40 |
| exact repeat | 2.7 ms | 4.4 ms | 40/40 |

Model load 381 ms warm-cache (machine-level weight cache; first-ever download
~6.9 s measured previously). Candidate card 289 bytes. The deadline cap on the
semantic tier is 120 ms; a cold model degrades to the lexical tier and warms
in the background.

## C. Production durable fan-out

**The seam.** `dispatch_background_task` gained an optional typed `manifest`
(canonical item ids, phases, missing-required-inputs) — the brain's own plan
carries the disposition; there is no second classifier call and no phrase
heuristic. Missing inputs return ONE typed clarification. Placeholder item
ids, duplicate phases, and cycles are refused at admission (pre-existing
pins in `work-disposition-integrity.test.ts`).

**The journal.** `src/execution/durable-fanout.ts`: an immutable plan
contract (full normalized disposition JSON) plus one SQLite row per
item×phase, written in one transaction. Identities are digest tuples.
Settlement is a CAS — a terminal `done` cannot regress, a retry observes
`alreadySettled`, and a settlement for an item the plan never named is
refused.

**The scheduler is the mature one.** Windows compile into real durable
`BackgroundTaskRecord`s processed by `processBackgroundTasks` — the same
runner, claims, restart recovery, and report-back as every other background
task. Workers settle through `fanout_settle_item` / page through
`fanout_list_open_items` (registered production tools).

**Reducer.** Readiness is a query over the journal (`fanoutReducerReady`),
never a caller array. `maybeAdmitFanoutReducer` admits the reduction as one
durable task through an atomic lease — proven once-only under four concurrent
claimants and across restart.

**Concurrency.** The drain's process-wide boolean guard became durable
capacity: a drain tick claims `policyCap − running` tasks, measured against
the durable running count. Two ticks landing while work is pending drive two
workers that genuinely overlap; the cap still bounds thrash.

**Proven at scale** (`durable-fanout-production.test.ts`, only the model
replaced): 40, 120, and 514 items each execute fully — correct window count
(514 → 3 windows), no truncation, overlap observed where >1 window — and
reduce exactly once. The crash test settles 17 of 40, dies mid-window,
reconciles (dead worker's window released, settled items untouched),
completes the remainder with byte-identical timestamps on the pre-crash
settlements, and still admits exactly one reducer.

**Explicit background without a manifest** compiles to the canonical one-item
durable contract — one item and five hundred ride the same machinery.

## B. Exactly-once continuation

**Transactional CAS.** Handoff records moved from rename-based JSON into
`src/execution/handoff-store.ts`: ladder check, revision CAS, and write are
ONE immediate SQLite transaction (`tx.immediate()` — a deferred transaction's
lock upgrade is the check-then-write race in a different costume). A handoff
may only be admitted as `requested`; identity (task, session, source event)
is immutable; capsule/task ids are additive; `terminal` is the rung that
stops reconciliation from resurrecting an ended transfer. Legacy JSON records
import once. Proven under 8-way in-process contention AND a genuine
two-process interleaving test (50 advances, spawned workers, one home).

**Order is the invariant.** `detachRunningTurnToBackground` writes the
durable transfer intent and checkpoints the capsule BEFORE `requestKill`
fences the foreground; admission failure ends the handoff and returns the
turn to the live foreground. The crash window that used to leave stopped
work with no owner now leaves a recorded handoff that boot reconciliation
(`reconcileIncompleteHandoffs`, wired in `startDaemon` next to task
recovery) converges to exactly one owner.

**Capsules from durable state.** `projectCapsuleFromDurableState` builds the
capsule's manifest/effect refs from the task registry and event log, not
caller prose; capsules digest-verify on load (pre-existing pin).

**Transferred, not cancelled.** A kill that handed the turn to a durable
background owner commits a `transferred` presentation naming the task
(`handoffTransferForSource` at the terminal reducer; `transferredToTaskId`
rides delivery metadata) — the user is told where their work went.

Suites: `handoff-store.test.ts` (6), `handoff-production.test.ts` (extended),
`continuation-integrity.test.ts` (kept green through the store swap).

## D. Unified activity

**The senders consume the reducer.** Both channel transports
(`runDiscordHarnessConversation`, which Slack also rides) drive their
placeholder/edit/final lifecycle through `createChannelProgressLane`: the
shared `reduceTransportProgress`/`applyTransportProgress` decide kickoff, the
20-second rate-limited milestone edits, and the single final replacement, fed
by `projectRunSnapshot` over display-state phase + the durable attempt row's
lease. The caller-less `nextSlackProgressAction`/`nextDiscordProgressAction`
wrappers are DELETED. Labels carry bounded phases, never tool names or
arguments.

**One server projection.** `projectActivitySnapshot`
(`src/dashboard/activity-projection.ts`) returns workflow runs, background
tasks, and live chat attempts in one typed list (schema version + per-entry
monotonic revisions derived from durable seq/updatedAt). The console route
serves it; `?workingNow=1` applies the server-side gate so ordinary
foreground chat stays inline and only detached/scheduled/long work surfaces.
Liveness derives from leases (`deriveRunLiveness`): a 90-second-quiet call
with a live lease stays live; an expired lease renders needs-attention; no
served field combination turns an unresolved terminal green (pinned).

Suites: `activity-projection.test.ts` (incl. restart reconstruction),
`channel-progress-lane.test.ts` (kickoff/rate-limit/final through a fake
handle), `activity-parity.test.ts`, full discord/slack harness suites.

and the alias learned from the answer turn ("use the first one") is weak.
The structural fix works when the ask is structurally marked; classifying
prose questions is deliberately out of bounds.
