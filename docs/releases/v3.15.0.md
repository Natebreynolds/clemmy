# v3.15.0 — a tool contract is learned once, and the feed narrates the work

Release type: performance + visibility release. Everything here comes from
one measured live run on the previous build: a single-email task that spent
more than a third of its tool calls looking up how to call tools it had
already been told to use. Suite at the cut: 9,382 tests, 0 failures.

## Discovery stops repeating itself

Capability resolution names the proven tools before the model takes its
first step — and the model then spent 11 of 29 tool calls searching for
those very tools (live 2026-08-07). Naming was never enough: the name
arrives as prose while the argument schema does not, so "I know which tool"
still cost a discovery round trip to learn how to call it. At that point
discovery is not a cheap HTTP call, it is a full model round trip mid-run.

Three changes, all behind the existing accessor so every caller benefits
without a new path anyone must remember to use:

- **Contracts are durable.** The schema cache that would have answered was
  an in-memory Map; it died with the process, so every restart re-paid
  discovery for tools used a hundred times before. Contracts are now
  fingerprinted, per machine, atomically written and bounded. Identifier
  kinds are deliberately unmodelled — Composio slugs, CLI commands and
  native MCP names round-trip identically, pinned with all four, so this
  cannot quietly become a Composio feature.

- **A successful call teaches how to call it.** A schema says what is
  legal; only a call that worked says what actually works. In the same live
  run, `OUTLOOK_UPDATE_EMAIL` failed with invalid arguments on a tool used
  successfully minutes earlier — the contract was known and the working
  payload was not, so recovery cost a model turn and a rewrite against the
  live mailbox. Contracts now carry a payload shape that worked. It records
  **shape, never content**: keys, booleans and numbers survive; recipients,
  subjects and bodies become type markers. A performance cache must never
  become a quiet copy of the user's mailbox, and the pin uses a live draft
  as its fixture.

- **Schemas warm at preflight.** Fetching a schema is I/O, not a decision,
  so it happens while the model is still reading — a background request the
  first time and nothing at all afterwards, because contracts are durable.
  Bounded to six, and it skips what the runtime already disbelieves: a
  previously-failed capability is not worth a fetch, and a toolkit with no
  live connection cannot answer one. Fire-and-forget by construction, so a
  slow or failing warm cannot delay the turn it was only trying to help.
  Kill-switch `CLEMMY_WARM_TOOL_CONTRACTS`.

One semantic deliberately unchanged: the fingerprint that lets a proven
procedure be *learned* still reads process memory only. A contract off disk
proves we once saw a schema, not that the provider still serves it —
validation may lean on the durable copy, learning may not.

## The activity feed narrates the work, not the mechanism

The feed was one row per tool call, in call order, with runtime diagnostics
rendered verbatim. That same live task read as nine "searching" rows, three
identical profile lookups, six mail writes, and a line reading "Grounded in
what's proven: 1 proven tool, 2 not connected".

Three rules, applied to both surfaces so the inline strip and the board
drawer cannot disagree about the same run:

- **Discovery is not work.** Finding a tool is overhead; narrating it is
  like narrating a walk to the filing cabinet. A *failed* lookup stays,
  because it is the reason nothing after it happened.
- **Repetition is one thing happening, not many.** Identical rows fold with
  a count, so a retry storm cannot bury the row that matters.
- **An attempt and its outcome are one row whose state changes.** Rendering
  them as siblings produced "Created a draft to X" directly above "Created
  a draft to X — failed", which made a clean failure read as chaos.

Nothing is destroyed: hidden rows are counted and a verbose mode returns
everything untouched. Narration may hide noise, never bad news —
unrecognised rows stay visible and a failure surviving the filter is
pinned.

## Known-not-fixed

The same live run made **six external writes for one draft** — two creates,
three updates, one delete — using the destination mailbox as a scratchpad.
Four advisories fired during that run and every one was ignored. That class
is not addressed here and will not be addressed by a fifth advisory.
