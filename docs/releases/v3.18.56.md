# v3.18.56 — Clem preserves unfinished questions and memory corrections

This candidate keeps harness schema 99. It combines the approved-call and
decline handling from Claude's branch with the reviewed question and memory
completion work. Publication and platform availability require the final
release gates; local candidate preparation does not publish a release.

## Questions and partial progress

- Clem's proposed question and the answer beside it are reviewed together
  before the question reaches the user. Repairs preserve the independent
  work already completed and any question that still needs an answer.
- Connection controls keep their own app and account binding. A separate
  question remains visible when connecting that app cannot answer it.
- The question contract applies to compatible-model tool calls as well as
  the native question wire. Jev uses the same quality requirements.

## Memory

- A request to update several memories stays unfinished while a target or
  conflict remains unresolved. Correcting one record does not silently drop
  the other requested work.
- Accepted, verified explicit saves can reach the existing whole-request
  completion review while duplicate automatic capture is still queued.
  Pending automatic-only work retains its completion hold.
- Answering a clarification can correct the outstanding memory using the
  current answer, the verified question history and the original project
  scope. The answer does not gain authority from assistant wording alone.
- Corrections require fresh current-request reads and unchanged canonical
  records. Deferred corrections and learned recovery routes retain their
  original evidence and cannot learn from an unreviewed result.

## Approved and declined work

- An approved carried call is checked and rebuilt under the same carrier,
  account, schema and requirement that produced its approval card.
- A declined action remains declined for that request. Clem's response to
  the decline is preserved instead of raising the same card again.
- Direct calls to Clem's own tools retain their argument validation. A list
  represented as JSON text follows the tool's existing list contract.
- Ordinary host turns appear in the diagnostic trace alongside graph work.

## Installation and evidence

The existing guarded hotpatch procedure can verify a retained interrupted
history against an independent baseline and preserve its rollback chain.
It refuses an installation when the app starts after the closed-app check.
Historical failed installations remain failed evidence; recovery does not
invent their missing receipts.

The named Mac memory acceptance sequence saved two separate synthetic facts,
corrected A, published the unresolved B question, then saved the answer for B
while preserving A. This establishes that scoped sequence on the tested
hotpatch source. The final versioned candidate still needs its own complete
release receipts. It does not establish global memory preservation,
multi-hop live behavior, all-provider usage or cost, or physical iPhone,
Duo, Watch or Windows acceptance.

The earlier widget, Watch and mobile changes remain included. This candidate
does not by itself produce a new TestFlight build or qualify those devices.

## Known limits

- An owner notification can still advance dependent workflow work before a
  required external send. That known limitation remains deferred; final
  whole-objective verification still prevents an unsent email from counting
  as completed external work.
- Some memory replies are more verbose than needed and make broader
  preservation statements than the scoped evidence proves.
- Earlier clarification before widening an unresolved people lookup is a
  separate guidance refinement; it is not implemented in this candidate.
- No latency or token-savings claim is made from incomplete or differently
  attributed tasks.
