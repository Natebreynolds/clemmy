# v3.18.56 — Memory stays, working copies decay; a faster reply path; honest status

**Database migration: harness schema 99 → 100.** The migration rewrites four
delete guards and touches no rows; it runs at the first start of this build.
A build older than this one does not open a schema-100 database, so a Mac
that has started v3.18.56 stays on v3.18.56 or newer. The Mac build comes
from the release workflow (signed and notarized). The Windows x64 build of
the same commit is qualified by the private Windows pipeline from this tag,
unsigned until a code-signing certificate exists.

Proven on the installed app with the first-owner scenario battery on the
owner's own brain (connections status, an underspecified ask, a partial
reply, workflow authoring with two connected accounts of one app, a batch
delete with one card, a timer) and with the live storage numbers below.

## Storage: memory stays, working copies decay

Memory — facts, preferences, episodes — is small and is never a candidate
for deletion; it fades only by disuse. What grew an install were working
copies: the full copy of every request sent to a model, the whole
conversation history re-saved at every step, raw tool results, and the
bookkeeping each turn needed while it ran.

- **Retention enforces its budget by default.** The daily pass now ends
  request copies no later turn reads back (keeping a running task's and the
  newest few of any recent chat) and tool results older than a week, after
  their facts are distilled into memory. An operator can set
  `CLEMMY_STORAGE_RETENTION=report` to measure only, or `off`.
- **A chat retired to its memory sheds its step records.** A day after a chat
  retires (idle a month, its summary written by your memory model), the
  batch records every turn wrote go. The transcript, the memory, and the
  request provenance stay. On the owner's install this freed 3.6 GB of rows
  on the first afternoon.
- **Stored histories are compressed.** The converter that packs step history
  into a shared compressed store now runs every idle minute, bounded,
  yielding to any unfinished work. It cuts that history about 2.6 times with
  no change to what any reader sees.
- Measured on the owner's install: the harness database went from 8.47 GB to
  4.49 GB after one offline rewrite; the home from 27.9 GB toward 14 GB once
  the first enforced daily pass runs.

## Faster replies and account routing

- **Your answer reaches Clem sooner.** A reply to Clem's question goes to the
  brain in about 7 seconds (was 18 on average, up to 100). A question Clem
  asks again after one review is delivered as the question; the phone no
  longer shows a question twice.
- **The remembered account is kept without a review.** When your words say
  nothing about accounts, a quick screen keeps your remembered or sole
  account in 0.1 seconds instead of a 4–6 second reviewer call; words that
  name an account still go to the reviewer.

## Honest status and refusals

- **Voice says when it cannot speak.** While the saved OpenAI key is refused,
  live voice reports unavailable with the reason instead of starting a
  session that cannot work; spoken replies fall back to the computer's voice.
- **Connections name their accounts.** Connection status carries each
  account's address, so Clem can tell you which mailbox has expired.
- **A misnamed field is refused, never silently dropped.** A read sent with a
  field its tool does not take is refused with the exact schema; a dropped
  field used to read a default target instead. `app_guide` now accepts the
  `topic` callers reach for.
- **An approved write runs on resume.** An approved workflow delete runs when
  the card is answered; a dispatch-time completion that broke this is gone.
- **A workflow's account is bound by its connection id.** A resource whose id
  is a connected account's own id is bound to it, so authoring with two
  accounts of one app no longer stops on "needs resource binding".
- A provider reply whose nested task failed and returned nothing settles as
  the failure it is instead of an error at settlement.

## Not in this release

The diagnostic rows in the event log (transport, retry and dispatch
bookkeeping) still accumulate; the reaper for them exists but is not
scheduled until the tables that reference events are indexed and the batches
run off the daemon's loop. Result handles and request provenance of retired
chats are the next levers.
