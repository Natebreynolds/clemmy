# v3.18.18 — a promise is not a result

Release type: defect-class removal. Every change here was root-caused from a
live run on an operator machine, and each ships with that failure replayed as
its regression pin. One change was deliberately NOT shipped, and one existing
pin turned out to have been dead for days; both are named below.

## The defect

Four separate symptoms, one shape: **Clem described work instead of doing it,
and the turn ended.** The owner's only way forward was to nudge.

Observed live, three consecutive turns on one machine:

> "I'll resolve that and turn it on, then run the first batch as the test."
> — *Stopped here — your work is kept*

> "Live verification is running now; it will enable automatically if it passes."
> — *Stopped here — your work is kept*

Each carried: *"I could not get this result independently reviewed, so it
stands unreviewed. The review model is not reachable with the current model
setup; the console has the details."*

The status badge read **`Claude 5h 100% · wk 12%`** with the brain on GPT-5.6.
Cross-family review routes away from the brain's own family, so every review
went to Claude, which was rate-limited out. The reviewer was unreachable on
*every* turn, and an unreachable reviewer returned `done: true`.

## What changed

**An unreachable reviewer no longer delivers the promise.** Jev already reads
the same reply on the same hot path; its verdict was computed, recorded as
`jevAttempt` telemetry, and then discarded in favour of `done: true` at the one
moment it was the only reviewer left. A Jev NOT-DONE now drives the ordinary
bounded continuation, so the harness does the work instead of announcing it.
One direction only: a Jev DONE still fails open, because *"the reviewer was
unreachable"* must never read as *"this was reviewed"*. `failedOpen` stays set
throughout, so nothing downstream claims a completed review.

**A promise is judged again on any turn that asked for something.** The gate
that exists precisely to catch *"I'll do that next"* had gained a conjunction
requiring `actionIntent || meaningfulToolEvidence || sourceWorkAttempted`. That
contradicted its own docstring — *"a promise-shaped reply is always judged"* —
and dropped the review on a **lookup**: *"Read the current harness status and
report it."* answered with *"I will read the status."*, nothing called yet, made
all three false, and the promise became the final answer. Two things in the
codebase already said this was wrong before any test ran: that docstring, and
`isConversationalReviewSkip`, which requires `promiseShaped === false` — so the
new skip category could not even be described, making it a *silent* skip with no
event. The intended exemption was chit-chat, so that is what is exempted now,
read from the intent union's own two no-work members rather than from "not an
action". A lookup is a request.

This one was caught by an existing pin, not in the field. It never shipped.

**The watcher keeps watching after it has stopped nudging.** A steer budget of
two was silencing the *watch*, not just the steer. Live: the watcher caught
drift at 90 seconds and said the right thing twice — *"publish the required plan
of substance now, before loading skills"* — both delivered, both ignored.
Injections hit 2 of 2, the gate closed, and the turn then ran unsupervised for
six more minutes, 90 tool calls and 282,762 uncached tokens, publishing no plan.
The owner stopped it. While drift is unresolved the check now still runs, and a
separate escalation decides whether that check may speak. `maxChecks` remains
the real bound. The escalation is recorded and **not yet enforced**.

**An unanswered account choice is a question, not a broken workflow.** Authoring
a workflow produced this, three attempts running:

```
query_accounts: error — 13 accounts are registered for
  "salesforce_sf_soql_query"; choose the exact account before this
  workflow can dispatch.
build_batch: failed — query_accounts is blocked with creation-test error.
Fix the flagged step(s) with workflow_update (e.g. bind the right tool),
  then re-test. To run it as-is anyway: workflow_set_enabled.
```

Three defects in one report: the owner was told to choose an account and given
neither the list nor any way to choose; a step that stopped *only because of
that question* was reported as broken, so one unanswered question read as a
failing workflow; and the way out was two engine calls, which are not things a
person does. The account count climbed 11 → 13 across retries, so every re-test
re-hit the same wall.

`executeStepVerified` raises the same typed `WorkflowCapabilityBlockedError` a
scheduled run raises — *"control flow, not a failed task"*, proven
pre-dispatch, carrying the bounded account choices — and the creation test
caught it in a generic handler that flattened it to `status: 'error'` with
`err.message`. Reason and choice set were discarded at that line, so nothing
downstream could ask. Authoring now reports `needs_choice` and renders the
enumerated question, taken from the same presentation a parked run uses, so
both ask it identically. Steps waiting on it are `unverifiable` — the honesty
already applied to steps downstream of a previewed mutation — so the cascade
stops. The draft still stays disabled, and the report asks for the answer and
states what follows it: bind, re-test, enable on a pass.

**Two dead ends given a next edge.** The unreviewed note was the only entry in
its table ending with no action for the owner — *"the console has the details"*,
which is useless on a machine whose owner is not the developer — while every
sibling ends *"Ask me to re-check it."* And a failed creation test now speaks in
Clem's voice rather than naming `workflow_update` and `workflow_set_enabled`.

## A pin that had been dead for days

`watcher-fanout-rearm.integration.test.ts` pins that a worker fan-out re-arms
the trajectory watcher. A later commit made the re-arm wait 30 seconds so a
quick batch would not spend a model call — and the fixture batch settles in
milliseconds, so the timer could never fire. It had been failing
deterministically, at HEAD, proving nothing, and it is not in
`test:release-closure` so nothing was red. The delay is now a configurable
accessor (production default unchanged at 30s) and the pin scales it.

## Honestly deferred

- **The root cause of the unreachable reviewer is NOT fixed.**
  `claudeAvailable()` returns `configured` with **no quota check**, while
  `codexAvailable()` directly below it checks quota — carrying a comment about
  precisely this incident on the other provider (*"every consumer kept dialing
  a lane whose plan was exhausted"*). The Claude 5h/7-day windows are already
  known to the daemon; they draw the status badge. Separately, completion review
  resolves a single lane plus a hedge rather than `resolveBoundaryJudgeChain()`,
  which three other callers already use — the owner-visible per-turn review is
  the one caller that cannot fall over. Not shipped because 3 of
  `claudeAvailable()`'s 14 consumers are brain routing, and a broad unvalidated
  change of that shape caused this same day's crash-loop.
- **An answered account choice does not yet resume the creation test in
  place.** `readmitCapabilityBlockedRun` readmits unconditionally as
  `status: 'running'`, which would turn a resumed creation test into a real run
  and actually dispatch the previewed `draft_emails` / `notify_ready` steps.
  That needs the pre-block status preserved across readmit, and it is not a
  change to make without pinning the mutating-step path first.
- **The watcher's `bound` escalation is recorded, not enforced.** A bound ends
  the owner's turn; it ships observational first.

## Release hygiene

The first candidate for this release was refused by the release gate for nine
hygiene violations. Four were measurement **run outputs** swept in by a
`git add -A`, each embedding the operator's name and email from the live
environment it measured; that directory is now ignored. The other four were
checkpoint docs that had carried a personal home path in the tree for two days,
because commits that never trigger a release dispatch are never gated.
