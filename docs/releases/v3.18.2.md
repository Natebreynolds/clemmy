# v3.18.2 — the daemon stays up, and the work it does can be seen, stopped, and switched on

Release type: correctness and product fixes on top of v3.18.1. Two threads, from
two sessions on the same branch: keeping the daemon alive and small, and closing
the loops where a user could see that something was wrong but could do nothing
about it.

## The daemon stays up

**A third party's slow handshake is not this daemon's health.** Discord's
gateway handshake timed out on a flaky network, `await client.login()` rejected
inside `startDaemon`'s onReady, and the rejection unwound through `main().catch`
to `process.exit(1)` — killing a daemon that had already bound its listeners,
finished boot reconciliation and was serving the app. The supervisor restarted
it, the next handshake timed out too, and 3.18.1 crash-looped four times in five
minutes, replaying ~35s of boot work over a 1.1GB database each cycle. A failed
BIND is still fatal; an outbound session to someone else's service is not.

**Ready means the door is open, not that every friend answered.** Measured from
that same boot: reconciliation done at +14.3s, webhook bound at +16.5s — and
then four more minutes inside onReady loading a local embedding provider and
probing CLI auth, during which readiness never advanced and HTTP could not
answer. Everything that makes the daemon useful was finished at 16.5 seconds.

**Two liveness signals that share a failure mode are one signal.** On a Zoom
call the daemon blocked in memory maintenance doing synchronous ONNX + SQLite
work on a CPU-starved machine. Its HTTP listener stopped answering and its
supervisor heartbeat went stale together — the heartbeat was a `setInterval` on
the very loop that was blocked, so the "busy but alive" deferral built for
exactly this case died with the thing it measured. A healthy daemon was
SIGKILLed into 16s+ of boot reconciliation. Inference now runs off the loop, and
the deferral no longer keys on a signal the same stall silences.

**Get out of the way when the machine is busy.** A vault reindex and an
embedding backfill ran while Zoom held 80–100% CPU. Neither was urgent, both
competed with the user's call, and together they blocked the loop long enough to
be killed as hung. Discretionary maintenance now yields under load, measured by
load average per core — never by recognizing which programs are running.
Reapers, settlement drains and retention work do not yield.

**A worker that cannot spawn degrades now, not in two minutes.** The embedding
worker's boot promise settled only on a ready/unavailable message or a 120s
timeout, so a worker that could not spawn at all left the first recall blocking
for the full two minutes before falling back to in-process inference.

**A rollback image you can no longer roll back to is just disk.** Full
`VACUUM INTO` copies were written at every schema boundary and never pruned, so
a long-lived install carried one whole-database copy per migration, forever. The
newest three are kept, nothing younger than 30 days is touched.

## The work can be seen, stopped, and switched on

**A board reads the data it was built from.** Every Space view Clem authors
renders from `window.__SPACE_DATA__`, and nothing in the runtime ever defined
that name — only the async `clem.data()` existed. A triage board holding 25
emails rendered its empty state, and the owner said "I am just not seeing the
emails I should see here". The served view now plants the dataset as a
synchronous global before any authored script runs, escaped so no dataset can
close its own script tag; the published snapshot plants the same global.

**A committed dataset repaints an open board.** The UI reloaded on the view
file's mtime alone, so a data commit — including a scheduled pull — never
reached a board the user already had open. The dataset now carries its own
stamp, and a repaint waits while the frame has focus so a half-typed draft
survives.

**"Just turn it on" needs a door.** `workflow_set_enabled` was discoverable and
uncallable: no `localPlanning` declaration, so no capability, so nothing for the
work_call door to bind and a refusal before dispatch. The only act that always
succeeds is creating a new workflow — so a user asking to enable one got a
duplicate instead. Enable/disable is declared like its twin
`workflow_unschedule`, and a census test now requires every model-reachable
workflow write to bind a door or say in writing why it does not.

**A workflow that is off comes to you with its own switch.** An edit that
changes what a workflow executes switches it off pending re-verification —
correct, but the only notice was a silent row and one line of chat. It now
raises a Needs You card naming the workflow, why it is off in plain words, and
the switch itself, performing the same validated enable as the Automate toggle.
A user-requested disable raises nothing.

**The Stop button stays where you are watching.** The trace drawer offered Stop
only for foreground runs; a background task's Cancel sat in a cockpit that
scrolls away under a feed pinned to its newest row, and execution and workflow
cards had no drawer stop at all. Stop now sits in the fixed header for any card
that declares it can be cancelled.

**A ceiling failure says what stopped it.** A scheduled workflow failed nine
runs whose only explanation was `tool calls per turn exceeded the limit of 64`.
This lane auto-resumes a ceiling, so the ceiling is never what ended the step —
what ended it is why the resuming stopped. The failure now names that, and the
budget knob behind it.

**A failed workflow list is not an empty one.** The Automate tab rendered an
unavailable list as "Let's automate something", inviting a user to rebuild
automations he already had.
