# v3.18.24 — the shell anywhere, two modes, connecting an app inside the task, and saved sources that run durably

Mac-only release. Harness schema moves from 82 to 88 in this release; the
upgrade contract for a v3.14+ home is in `docs/V314-UPGRADE-REHEARSAL.md`.
Qualification and live evidence are recorded below as they were measured;
signed and notarized artifacts are produced by the release workflow and are
not claimed here.

## What changed

### The shell, anywhere

- A shell command that changes local files (`cp`, `mkdir`, `git commit`, an
  install, output to a file) runs as ordinary local work on a chat turn: no
  plan, no card. Before this release such a command was refused with no path
  to ask. Reads and computation keep their own envelope.
- A shell command that leaves the machine (a web POST, `git push`, a deploy)
  is never run from the turn. The turn opens one card whose preview is the
  exact command; approving it runs that command once and reports what landed.
  No model turn is spent after the approval.
- The guards inside the shell are unchanged and run on every path: hard
  blocks, credential refusal, protection of Clem's own stores, the long-wait
  refusal, the starting-folder rule. An approved card cannot carry a command
  those guards refuse.
- A page Clem wrote can be looked at as a browser shows it (`page_preview`),
  and a project's pages open in the app: framed on the desktop, as pictures
  on the phone. Reading an `.html` file says so. A linked local project's
  own commands and instructions are offered to the turn.
- `docs/SAFETY-MODEL.md` describes every guard, where it runs, and what it
  does not cover.

### Two modes: Auto and Ask

- Settings has one approval control. **Auto** (the default): anything that
  is not disruptive runs — local files, the shell, reads, ordinary changes in
  connected apps. **Ask**: an ordinary change in a connected app also waits
  for the owner the first time; the approval teaches that kind of change
  (the operation on that account, read from the receipt) and it runs next
  time. A send, a delete, an irreversible or administrative change, a sealed
  bulk change and a command that leaves the machine ask in both modes.
- Learned kinds are listed in Settings and can be forgotten; a kind unused
  for sixty days is forgotten on its own.
- The Run limits page is gone. Run limits are fixed: a run stops for a
  terminal outcome, a gate, a stop, or zero progress, never for a ceiling.
  Under the unlimited preset a workflow step carries no clock.
- The folder wall that the old "Approve" setting raised around files and
  the shell is gone in both modes; the guards inside the tools stand.

### Connecting an app inside the task

- When a task needs an app that is not connected, setup happens in the
  conversation, on the desktop and on the paired phone, from the provider's
  own metadata. The exact provider-returned account is verified, the
  original task stays visible, and it continues once when the account is
  ready. Reopening, a lost response and retry keep the same continuation.
- A reviewed Execute that pauses on a missing connection connects the app
  and reports that its execution remains paused; it is not restarted by
  setup. (Its resumption is a later slice.)
- Task budgets and usage are retained through connection recovery, and a
  resumed task's usage is attributed to it.

### Saved sources, refreshes and approvals

- A Space's saved source scripts run through an exact durable carrier with
  ownership, cancellation and owner controls (stop, resolve); a refresh
  report is recovered without replaying a completed script. A scheduled
  refresh binds to its saved read source. Simultaneous source failures are
  grouped; a trust approval is not offered where nothing could execute it.
- A queued action's card opens on the host engine as promised, and an
  approved card linked to one stored action runs that action itself and
  settles with what landed. The desktop approve button awaits that one
  execution instead of racing it.

### Workflows

- A workflow write whose constraint checker cannot answer is no longer sent
  back to the model as "reconcile before dispatch". The checker says what
  happened to it and retries a timed-out review once as a plain read; an
  unjudged write runs only under the owner's own exact approval, and
  otherwise the step finishes truthfully with that write named as not done.
- Workflow scripts and the child processes they own stop on cancellation.
- Daemon recovery is bounded and owned by each startup attempt.

## Known limits

- The phone has no mode control yet; the mode is set on the desktop.
- A host consent card for a local call with no plan (a credential-path
  `write_file`) cannot dispatch after approval; found by reading, not yet
  fixed.
- Kernel confinement of a command (macOS sandbox) is not built; the guards
  are in the tool, not the system.
- A reviewed Execute paused on a missing connection does not resume from
  setup; see above.
