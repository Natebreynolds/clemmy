# v3.18.41 — Workflows rehearse and run through one path, and Stop always stops

**Database migration: harness schema 94 → 95.** One additive table
(`outcome_reports_pending_v1`, the background-result outbox); no existing row
changes. An older build refuses to start on a v95 database, so going back to
3.18.40 or earlier after updating is not supported. The Mac build comes from
the release workflow (signed and notarized). The Windows x64 build of the
same commit is qualified by the private Windows pipeline from this tag,
**unsigned** until a code-signing certificate exists.

## A rehearsal and a run prepare a step the same way

- **One reading of `{{ … }}` references.** A field of an earlier step's
  output (`{{ steps.gather.output.title }}`, with or without spaces) fills in
  the same way whether it is the whole argument, text inside one, or part of
  a step's instructions. Before, it stayed as literal braces inside text, and
  a saved note could contain the template instead of the data.
- **Clear outcomes before anything is written.** A structured call's
  arguments come out as ready; missing data (a step output never produced, a
  field it doesn't have, an input the workflow never declares); data only a
  real run produces (a change the rehearsal only previewed); or refused by
  the tool, with the exact reason. A declared input left empty is data, not
  missing. A run refuses missing data instead of writing an empty value.
- **A rehearsal checks a write the way the run will.** It fills in the
  previewed step's arguments from real upstream data and compiles the call
  against what is connected here, so a missing connection, an account to
  choose, or a bad argument shows in the test, not on the first run.
- **A step that never ran is not a pass.** It reads "did not run" (something
  above it is outstanding); a check deferred until after a previewed write
  reads "checked on the first real run" and still passes.
- **A passed rehearsal counts.** The Workflows page shows a tested version as
  ready to turn on, and turning it on doesn't test it again; any edit other
  than on/off needs a new test.
- **Unmarked steps are read once.** A prompt step that doesn't say whether it
  writes is read once by the quick-check model, and the answer is saved
  against its prompt, skill and tools; a change reads it again, an unchanged
  rerun reads nothing. It decides what the step is, never what a call may do.

## Turned-on workflows don't stop for ordinary writes

- A workflow you saved and turned on makes its ordinary writes (drafts, rows,
  records) without a card, including a step that finds the exact operation
  while it works. Each call is still checked against the current connected
  account, definition and arguments. Sends must be named by the step; delete
  and admin operations are never covered this way.
- A run resumed after a stop carries the authority of the run it continues.

## Stop always stops

- A turn you stop while it is held for recovery ends stopped: one result, the
  attempt finished, no further model work. This holds across a restart, an
  expired run lease, and a first failed attempt to publish the result.
- A recovery that cannot start (its owner, source or evidence is gone) stops
  at once instead of retrying. A workflow parent's held turn is re-driven by
  its own owner, never by a timer holding a lease it already released.

## Background results arrive without interrupting you

- A finished background result (a workflow run, a background task) is
  committed with a durable publication intent and delivered from a retry
  outbox, so it reaches the chat once even across a failure or restart. It
  no longer waits for the chat to go idle, and it never takes over or steers
  the conversation you're in.

## Files, reports and history

- A relative file path lands in `~/.clementine-next/files/`, never inside the
  installed app (where it changed the signed app and was lost on update).
- Reports and replies no longer show a write tool's machine receipt.
- Clem can list a workflow's runs and read any step's full output; the
  Workflows page run view has "Ask Clementine about this run".
- Workflow status and history read one lightweight run inventory that
  re-reads only changed run files and notices a run finishing.
- A workflow edit that changes nothing settles as no write (it had caused a
  false "blocked" on a finished turn).
- A server's tool-sorting card asks only for a tool Clem chose, and names it.
