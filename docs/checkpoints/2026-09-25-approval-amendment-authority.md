**Problem and behavior.** The shared approval parser accepted the start of a message as authority for an unchanged action or plan. The newer conversational router skipped interpretation for any parsed decision of four words or fewer. “Go ahead but shorter,” “approve with changes,” and “confirm different recipient” could therefore authorize the old operation. Registry-owned live waits, background-task continuation and plan approval also use the shared parser without passing through the amendment router.

The parser now recognizes complete existing decision forms, with one optional exact approval ID, whitespace/case normalization and assertion punctuation. Conditions, questions, additional instructions and mixed decisions remain conversation. This is not a blacklist of amendment words. The pure implementation lives in approval-intent.ts; discord-harness keeps its existing exported entry point, so all current callers retain the same API. Bare yes/no remain non-authoritative without an explicit ID, as before.

The conversational router selects among all actionable formal approvals before checking executor support. A queued card still counts as a competing target. One explicit reference can select a card for amendment without granting approval. Multiple, missing, malformed, expired and unsupported targets do not fall back to a different card. Revalidation after asynchronous interpretation prevents a delayed amendment from acting on a resolved or expired card.

A second prefix boundary existed in the gateway's separate answer-forwarding handshake. After offering to forward “Monday” to a paused task, it treated “yes but use Tuesday” as confirmation and queued the old Monday answer. A regression reproduced the task incorrectly transitioning to pending with the old answer. The existing confirmation vocabulary now matches the whole reply, preserving bare yes and punctuated Yes!; qualified replies take the existing foreground-conversation path with their complete wording. This handshake deliberately retains its own vocabulary: bare yes confirms a particular proposed answer here, but is not formal write approval elsewhere. No lifecycle, task-selection or model policy changed.

Qualified replies can produce a sure change or decline, but cannot gain approval authority from Jev alone. Unavailable/uncertain interpretation suppresses any supplied legacy prefix decision. Exact parser decisions keep the existing zero-model executor path. Mobile's bare exact decline, whose caller supplies parsed:null, selects the sole supported card and rejects deterministically with no Jev call. Mobile bare approval is not expanded.
