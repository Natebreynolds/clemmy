# Proactivity beyond workflows: remember, notice, invite, act

Owner direction: Clem should make memory work understandable and offer useful goals, Spaces, and skills from retained knowledge and current context. Workflow suggestions are only one case. The experience should invite the user's context and grow with them without becoming an interruption stream.

## Product behavior

These are illustrative offers, not facts about this user or hardcoded templates for particular integrations:

| What Clem has evidence for | Useful offer | Context she may need |
| --- | --- | --- |
| An explicitly stated ambition plus recent related work, with no matching active goal | “You mentioned wanting to improve this. We now have a starting point. Want to turn it into a goal?” | What outcome would count as success, and whether a date matters |
| Related work repeatedly spread across chats and artifacts | “I can bring these into one Space so you can keep track of them.” | What belongs together and which information should stay in view |
| A successful procedure with retained corrections about how the user likes it done | “This approach worked, including your changes. Want me to save it as a reusable skill?” | Whether the procedure is a general preference or specific to this project |
| Memory repair or consolidation actually completed | “I organized these related notes and kept your latest correction.” | No question unless a real ambiguity remains |
| A memory review found a possible conflict but made no changes | “These two details may disagree. Which applies now?” | The exact missing distinction, not a generic “what next?” |

The first three are suggestions, not active goals or autorun authority. Choosing to shape an offer should open a conversation with the evidence and draft already attached. A useful response may refine or reject the premise. Do not force a long form or start a workflow for a simple Space or skill request.

## Two distinct channels

**Learning/activity receipts:** actual inspected, organized, corrected, superseded, or applied work. Receipts must say which occurred. Quiet reviews and housekeeping do not create unread decisions. Details belong in Memory; meaningful outcomes may appear in the existing Home progress surface. Running work stays in kanban.

**Contextual offers:** a useful next step with a short “why this, why now,” evidence references, and a concrete outcome. Optional offers should not inflate the urgent Needs you count. A question that blocks an accepted task belongs in the existing check-in/Needs you path. Review of a personality change keeps its existing explicit proposal semantics.

Coordinate presentation with the UI agent's active redesign. Reuse the existing Home composition rather than adding another dashboard panel by default.

## Framework direction

1. Consume changed durable evidence from memory, current goal revisions, and receipt-verified outcomes. Preserve source IDs, scope, and revisions. A suggestion generated by Clem is not new evidence of user interest; exclude this feedback loop.
2. Reconcile against existing goals, Spaces, skills, workflows, and earlier offers. Update an existing relevant object when appropriate rather than generating duplicates. Superseded facts and declined offers cannot silently reappear under a different title or artifact kind.
3. Select the appropriate outcome: goal, Space, skill, workflow, or a context question. The current workflow-suggestions watch is too narrow to own this entire decision. Do not overload AutomationOpportunityV1, which is specifically a workflow review/compilation contract.
4. Keep a durable offer identity with supporting evidence, relevant scope/revision, reason, proposed outcome, and disposition. Reuse existing proposal/check-in lifecycle infrastructure where it fits; do not build a second scheduler. Dismissal, postponement, acceptance, supersession, and expiry must survive restart. Acceptance must reference the exact reviewed generation.
5. On acceptance, recheck evidence and duplicates, then use the ordinary tool discovery and authoring paths. Goals use the canonical goal writer, Spaces use existing Space creation, skills use existing distillation/validation, and workflows use the workflow authoring path. No new chat verbs, provider-specific branches, or hidden activation of recurrence.
6. Learn from the user's response within its scope: “not useful,” “later,” and “wrong assumption” mean different things. Do not treat silence as consent or infer a universal preference from one dismissal. Re-offering needs relevant new evidence or an explicitly requested revisit.

## Efficiency

Use existing cadence, quiet-hours, discretionary-work deferral, and user attention policy. No separate polling loop. Unchanged evidence should require no model invocation. Coalesce changes and prepare a bounded evidence packet; never replay the entire vault or conversation history each heartbeat. Use small workers for bounded synthesis and Jev for supported narrow decisions where needed; deterministic dedupe and lifecycle checks stay in code. Do not invoke both simply because they are available.

Measure changed versus unchanged checks, proposals accepted/declined, repeated-offer suppression, latency, and tokens. Do not optimize for more check-ins. The outcome is useful accepted work with less repetition.

## Implemented first slice in this branch

The report-only memory curator previously wrote a report and log without a shared operational receipt. It now emits `memory_review_completed` through the existing operational telemetry store/action bus after report persistence. The receipt contains aggregate counts and finding categories, not raw facts, names, or recommendations. It explicitly records `mutationApplied: false` and `modelCalls: 0`. Identical aggregate receipts on the same report day deduplicate.

This is a visibility foundation, not the general offer engine and not a claim that memory was repaired. The UI has not yet been wired to present this new event. Existing `/api/console` operational-event consumption should be reviewed with the UI agent; do not add a parallel feed.

Regression pin: expected one receipt after two identical reviews; before the fix there were zero (3 passed, 1 failed). Tests also assert no private memory text enters the receipt. Validation logs: `/tmp/curator-receipt-before.log`, `/tmp/curator-receipt-after.log`, `/tmp/curator-receipt-types.log`.

## Acceptance still required

- Controlled memory review is visible as a review, not an applied repair; applied changes have their own evidence.
- One evidence-backed goal offer, Space offer, and skill offer each reaches the correct ordinary creation path after the user's response.
- Missing context is carried into a concise check-in; the answer resumes the same offer instead of starting over.
- Decline/snooze/correction persists across restart and prevents repeated offers, including offers reframed as another artifact kind.
- Duplicate acceptance creates one durable object. Changed evidence invalidates a stale offer. Existing suitable objects are reused.
- Desktop and mobile agree on pending decisions and resolution. Optional suggestions do not masquerade as urgent blockers.
- The installed combined app passes these cases against controlled live-home fixtures with measured latency/calls/tokens. No live savings or completed offer implementation is claimed yet.
