## 2. The calendar watch names no operation — `claude/calendar-discovery`

- `7bf049c88` The watch was bound to two provider operation ids with their
  own argument and field mappings. It now learns each connected provider's
  read: the judge role reads the provider's current definitions once
  (`deriveCalendarRead` on the semantic port) and writes a recipe — which
  operation lists events in a window, which arguments carry the window,
  where an event's id, title, times, status and the owner's response live.
  Stored in `state/calendar-read-recipes.json` against the definition's
  fingerprint (the receipt); derived again when the definition changes, or
  once with a sample when a recipe reads nothing out of a non-empty
  response. A provider with no window read is left alone; a missing model is
  named and retried after thirty minutes, never guessed. Pins:
  `calendar-read-learning.test.ts`, `calendar-watch.test.ts` (recipe
  fixtures replace the two parsers).
- Live acceptance owed: on the installed app the owner's connected calendar
  must get a recipe on the first tick after install (watch the daemon log
  for "learned the provider's calendar read"), and the next tick must read
  the same events the previous build read. The old state file carries no
  recipes, so the first tick after install spends one judge call per
  connected calendar provider.

## 3. Review cost — `claude/calendar-discovery` (same branch)

- Measured on the live home (usage log, 09-30 → 10-01): the owner's
  channel-review run spent 35 reviewer rounds / 913k prompt tokens / 44k
  output tokens on eight per-write reviews of ordinary row appends; each
  review opened with a ~20k-token base and took 3–5 evidence rounds,
  60–100 s. The base was the whole run's settlement list, each settlement
  wrapped in its own paragraph of rules (26–34k chars by the end of a run,
  measured on an APFS clone of the live DB with the install's seal key), and
  every write ran the full review at the provider's default depth.
- `3518bdae9` The per-write review reads a compact index (rules once, one
  numbered entry per settlement with its sealed request and result, the same
  retained refs): 26k → 12k chars on the same run. And it has stakes: an
  ordinary recoverable write (`authoredCatalogGate` = `ordinary_write`, or
  the exact reversible/ordinary local branch) is read at `effort: 'medium'`
  first; only a conflict, an uncertainty or a checker failure brings the full
  review, whose verdict decides; a send keeps the full review from the start.
  The completion review keeps the full evidence form. Pins:
  `workflow-mutation-review.test.ts` (stakes), the executor's evidence test
  (compact index). 1,167/1,167 across the 33 neighbouring files.
- `cbb95cc9c` The review prompt leads with the parts a step keeps
  (instructions, tool, schema) and ends with what changes (arguments,
  observations, digest), so the eight reviews of a run cache their base
  instead of each paying it uncached (every first round of the 09-30 run
  was cached=0).
- `e95887d07` The view carries `valueProvenance`: for each proposed value,
  the retained results that contain it verbatim. The reviewer's lookups
  mostly answered "where did these values come from" and "does the

- Live A/B owed: rerun `platform-49-slack-channel-review` on the hotpatched
